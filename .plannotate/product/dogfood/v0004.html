把 plan review 变成 PR 里的原生工作流

上一版建立了架构契约；本轮把契约落到评审体验的两处硬伤：图表必须像文字一样可评论、可定位；GitHub 的 pending review 冲突必须在 composer 原地恢复，而不是把评审者赶去新标签页。plan 保持原貌，GitHub 仍是唯一事实源。

Owner: maintainersStatus: implement in this PRVersion: v0004Source: examples/plannotate-dogfood.html

第三轮 dogfood 的三条结论

图表是方案的一等公民。plan 里的 SVG 一般是方案说明图表，必须能评论：媒体块继承 figure 的 data-plan-anchor，标签取 SVG 的 title，评论定位从“[图] svg”变成“[图] 系统上下文图”。

评审流程的失败要原地恢复。同一账号在一个 PR 只能有一个 pending review；v0.2 靠新标签页处理冲突，违背了 ADR-01 的原生原则。v0.3 在 composer 内检测冲突，提交或丢弃后自动重发，草稿全程保留。

评审层仍不能重排 plan。这条从第二轮延续并加严：现在总体意见、历史版本与无法定位的线程也统一进入 review rail，plan DOM 只承载高亮，viewer 不再有第二条渲染路径。

建议评审顺序

GitHub 建议给 reviewer 明确说明为什么改、改了什么、应重点看哪里。本 plan 按四个问题组织阅读，既降低人类认知负荷，也为 LLM 提供稳定的检索顺序。

  1. 01 · Scope系统边界与唯一事实源是否正确？
  2. 02 · Runtime读取、校验、评论的链路是否闭环？
  3. 03 · Decisions选项、取舍和后果是否明确？
  4. 04 · Quality验收是否可测、风险是否可控？

目的：说明 Plannotate 在 GitHub 协作环境中的边界。图中每条关系均标注方向与协议；虚线代表不可信内容跨越沙箱边界。

目的：让安全与实现 reviewer 看清哪段代码能接触 token，哪段代码只处理不可信 plan。评论 rail 与 plan 视觉分栏，但仍保持同一 review 上下文。

Runtime · 打开与评论时序

C4 静态图之外补一个关键运行场景：Reviewer 从 PR 进入 plan review，查看器校验 artifact，再把评论写回 GitHub。

架构决策记录

每条决策都包含上下文、选择与后果，避免只留下“用了什么”却没有“为什么”。

Accepted

ADR-01 · PR 内嵌工作区

Context: 新标签页丢失 PR 导航上下文。

Decision: 在原生 tab 列加入 Plan review，内容区切换为 extension iframe。

Consequence: 更像 Files changed；需容忍 GitHub DOM 演进。

Accepted

ADR-02 · 评论独立 rail

Context: inline cards 会改动 plan 网格和表格。

Decision: plan DOM 只加高亮 class，线程卡统一进入右侧 rail。

Consequence: 保真度提高；窄屏改为上下堆叠。

Accepted

ADR-03 · 自包含语义 SVG

Context: 远程 Mermaid/图片破坏离线与安全边界。

Decision: 图表使用内联 SVG + title/desc + 图例 + 文本摘要。

Consequence: 人类和 LLM 都可读；作者需维护图与文字一致。

Accepted

ADR-04 · pending review 原地恢复

Context: GitHub 限制同账号每 PR 一个 pending review，评论创建返回 422。

Decision: viewer 用 REST reviews API 检测冲突，composer 内提供“提交并重发”“丢弃并重发”，丢弃需两步确认；保留 GitHub 页面兜底。

Consequence: 评审者不离开 Plan review；丢弃是破坏性操作，必须显式确认。

Accepted

ADR-05 · rail 承载全部线程

Context: v0.2 的历史版本线程渲染在 viewer 顶部，与 rail 双轨维护。

Decision: 当前版本、总体意见、历史未解决与无法定位线程统一由 sandbox rail 分组渲染，viewer 只负责编排与 GitHub API。

Consequence: 单一渲染路径；rail 需要清晰的分组标题与版本徽标。

质量目标必须落成可观察场景。下表覆盖使用、变化与失败三类关键情境。

风险、缓解与非目标

风险影响缓解本轮边界
GitHub DOM 演进tab 或挂载点消失语义 aria-label + href 组合定位；MutationObserver 重建；失配时不隐藏原内容接受有限 DOM adapter，不注入 React 私有状态
图文漂移LLM/人类形成不同模型每图附机器可读摘要、图例、版本和验收；review anchor 单独定位不引入远程绘图库
信息密度过高阅读疲劳四步 review order；C4 只用 L1/L2；runtime 只记录关键场景不穷举组件/类图
误丢弃 pending review删除评审者在 GitHub 起草的评论丢弃按钮两步确认并显示草稿数量；提交是默认推荐路径；保留原生页面兜底不代替用户自动丢弃，任何删除都由显式点击触发

交付切片

Slice 1
图表锚点与标签：媒体块继承 figure 的 data-plan-anchor，quote 取 SVG title；旧版本 sidecar 不变。
Slice 2
composer 内 pending review 检测、提交/丢弃与自动重发；丢弃两步确认。
Slice 3
总体意见、历史版本与无法定位线程并入 review rail，移除 viewer 双轨渲染；沙箱内删除改为内联确认。
Slice 4
发布不可变 v0004，回复既有线程并保持 v0001–v0003 哈希不变。

本轮验收

  • 悬停三个 C4 图可直接评论；composer 与 rail 显示“[图] ＋ SVG title”标签，锚点继承 figure 的 data-plan-anchor。
  • 已有 pending review 时发表评论：草稿保留，composer 内提交或丢弃后评论自动重发成功。
  • 总体意见与历史版本未解决线程都在右侧 rail 分组显示，可回复；plan 列只有高亮不重排。
  • v0004 的三个 SVG、表格和布局保持源 HTML 原貌，评论不会插入其 DOM。
  • token 仍只在 extension storage/viewer；sandbox 无网络、表单和同源权限。
  • manifest 追加 v0004，v0001–v0003 的 HTML 和 sidecar 哈希不变。
